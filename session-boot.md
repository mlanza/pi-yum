# session-boot

## Purpose

`session-boot.js` is a session bootstrap extension that runs shell commands from rc files and posts their output into the conversation.

The point is to **dynamically preload context** into the model window from trusted sources at session start.

That makes it similar in intent to `AGENTS.md`:
- `AGENTS.md` = static guidance loaded as text
- session boot rc = dynamic guidance generated by scripts

So this feature is **scripted context injection**, delivered as user-level context—not a replacement system prompt.

---

## Why this exists

Sometimes the most useful context is not a fixed file. It may come from:
- command output
- current project state
- local tooling (`nt`, `cmd.js`, etc.)
- environment-dependent values

A scriptable session boot allows context to be fresh and computed at runtime.

---

## Safety model (why `grant` / `revoke` exists)

These rc files are scripts. Scripts can do harmful things.

To reduce accidental or malicious execution, each rc file must be explicitly trusted.

Trust is enforced by:
1. A required env secret: `SESSIONBOOT_PASSKEY`
2. A checksum line in each rc file: `@XXXXXXXX`
3. Verification that checksum matches file body + passkey-derived hash

If verification fails, commands do not run.

Only `SESSIONBOOT_PASSKEY` is used. Renaming the rc files does not change their contents or invalidate their checksums, provided the passkey value stays the same.

### Security intent

- `grant` marks current file contents as trusted (writes checksum)
- `revoke` removes trust marker (removes checksum line)
- Any edit to file body invalidates prior checksum until re-granted
- Without passkey, execution is blocked

This is a practical “signed script body” pattern for local bootstrap scripts.

---

## Discovery and boot order

On session start, the extension checks rc locations in order, but only executes bootstrap for:
- `reason: new`
- `reason: startup` when launch is **not** continue mode

It intentionally skips bootstrap when pi is launched with continue mode (`pi -c` / `--continue`), and also skips on `resume`, `fork`, and `reload`.

You can disable the extension for a run with:

```sh
pi --no-session-boot
```

When this flag is present, the extension does not wire up its renderer, command, or bootstrap session hook.

When bootstrap is eligible, it checks rc locations in order:

1. `./.sessionbootrc` (cwd local)
2. `$XDG_CONFIG_HOME/session-boot/.sessionbootrc` (defaults to `~/.config/session-boot/.sessionbootrc`)
3. `~/.sessionbootrc`
4. `~/.pi/session-boot/.sessionbootrc`
5. `~/.pi/agent/.sessionbootrc`

It does **not** stop at first hit.
It loads and processes **all existing matches**.

---

## RC file format

Expected format:

```text
@ji349dfH
# comments allowed
echo "hello"
cmd.js help
```

Rules:
- First line should be checksum: `@` + 8 alnum chars
- Body is everything after first line when checksum exists
- Body is executed as one shell script (`sh -lc`) with one process exit code
- Nothing is pre-parsed line-by-line by the extension

---

## Hash/check process

For each discovered rc file:

1. Parse with `readRC(raw, passkey)` into:
   - `checksum` (from first line, without `@`)
   - `body`
   - `hashkey` (computed)
   - `safe` (bool: `checksum === hashkey`)
2. `hashkey` is first 8 chars of a SHA-derived digest of:
   - `SESSIONBOOT_PASSKEY + "\n" + body`
3. Execute only when `safe === true`

---

## Runtime behavior

### When no rc files are found
- Does not inject a message. Use `/session-boot locate` to inspect checked locations.

### When passkey is missing
- Emits per-file warning (`⚠️`)
- Skips execution for all files

### When checksum line is missing
- Emits per-file notice (`🔒`)
- Skips execution for that file

### When checksum mismatches computed hash
- Emits per-file mismatch notice (`☠️`)
- Includes both `checksum` and computed `hashkey`
- Skips execution for that file

### When file is safe
- Runs the full rc body as a single shell script with timeout guard
- Captures stdout/stderr and one script exit code
- Emits `❌` when exit code is non-zero (including timeout)
- Emits `✅` when exit code is zero
- `stderr` is shown when present, but by itself does not force failure

---

## Output shape

Per-file bootstrap output is structured for scanability:

- Header line: emoji + rc path
- Optional detail line (shown on failure; includes exit code)
- Script body
- `↓↓↓` separator
- Command output, followed by stderr when non-empty

## `/session-boot` command

Manage trust markers from the CLI:

```text
/session-boot grant [--local|--global]
/session-boot revoke [--local|--global]
/session-boot locate [--local|--global]
```

Scopes:
- default: all discovered rc locations
- `--local`: only `./.sessionbootrc`
- `--global`: all discovered locations except local

### `grant`
- Requires `SESSIONBOOT_PASSKEY`
- Re-reads each target file at command time
- Computes checksum from current body
- Writes checksum line + body

### `revoke`
- Re-reads each target file at command time
- Writes body without checksum line

Re-reading at command time avoids stale in-memory assumptions.

## Exit code strategy: first failure vs aggregate

Because rc is now executed as one script, you control failure policy in the script itself.

### Stop on first failure (strict)
Add strict mode in rc when you want an immediate stop:

```sh
set -eu
set -o pipefail
# commands...
```

Notes:
- `pipefail` is shell-dependent; this runner uses `sh -lc`.
- On shells that do not support `pipefail`, that line will error; if needed, guard it or avoid it.

### Continue and track your own status (lenient)
If you want to keep going and decide final success yourself, capture return codes and `exit` at the end.

```sh
status=0
cmd_a || status=$?
cmd_b || status=$?
cmd_c || status=$?
exit "$status"
```

You can also keep the first failure specifically:

```sh
status=0
cmd_a || [ "$status" -ne 0 ] || status=$?
cmd_b || [ "$status" -ne 0 ] || status=$?
exit "$status"
```

This gives deliberate control: fail-fast when important, or run through and summarize.

## Operational guidance

- Treat rc scripts as privileged code.
- Keep bodies short and auditable.
- Prefer read-only context gathering commands.
- Re-run `grant` after any intentional body edit.
- Use `revoke` when temporarily disabling trusted execution.
